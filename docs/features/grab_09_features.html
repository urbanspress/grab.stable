How profile-driven compilation works

Instead of compiling cold one-off setup code or slowing down startup, GRAB watches which parts of your program actually run often and compiles only the hot paths into compact bytecode.

1 · VALIDATESource code is parsed and checked once, exactly as before.
2 · PROFILECold scripts run immediately on the AST interpreter while counters watch hot routes, functions, and loops.
3 · COMPILEHot units lower to a clean IR with numbered variable slots and compact, verified bytecode.
4 · EXECUTEThe VM runs hot code with fewer allocations and exact same outputs, errors, and safety limits.

Key pillars in plain English

01 · Hybrid Tiering (ADR-003, ADR-013)

Fast startup + fast hot paths

Cold startup code and one-shot CLI scripts run immediately on the AST interpreter. Once a function (16 calls), loop (64 iterations), or server route (8 requests) warms up, GRAB compiles it once per app generation.

Developer: zero syntax changes and instant CLI startup.
Visitor: busy web pages and APIs respond with lower latency and less memory churn.

02 · Semantic Equivalence Gate

100% identical results & errors

The bytecode VM is tested head-to-head against the AST interpreter on every conformance test. Exact base-10 decimals, yes/no Booleans, nothing, try/catch codes, and do together order stay identical.

Developer: switch between --engine=auto, ast, and vm with no surprises.
Visitor: zero subtle rounding bugs or changed behavior under load.

03 · Safety & Determinism Guards

Same strict limits inside the VM

The VM enforces the exact same 1,000,000-step loop guard, 256-frame call stack limit, request timeouts, and capability permissions—plus a static bytecode verifier before execution.

Developer: runaway loops and deep recursion still stop cleanly with exact line/column numbers.
Visitor: protected against hangs, crashes, and permission bypasses.

04 · Evidence-Based Benchmarks (ADR-016)

Measured speedups on real workloads

Verified against internal/interpreter and internal/server benchmarks: prepared function-call recursion runs ~3.0× faster with 95% fewer allocations (349 → 16), try/catch paths run ~3.1× faster with 59% fewer allocations, tight loops run 2.33× faster, compute JSON HTTP routes run ~2.0× faster, and cold auto scripts add ~2–4% startup overhead.

Developer: transparent before/after numbers on real GRAB workloads.
Visitor: smoother traffic handling without trading away correctness.

Engine modes & safety boundaries

Setting / GuardBehavior in GRAB 0.9
--engine=auto (default)Runs cold code on AST; compiles hot functions (16 calls), loops (64 iterations), and routes (8 hits) to bytecode.
--engine=astForces the pure AST reference interpreter (useful as a semantic oracle for debugging).
--engine=vmCompiles all validated functions, routes, and units upfront (used for conformance parity and benchmarks).
Loop & stack limitsNon-catchable GRAB-E307 at 1,000,000 loop steps; GRAB-E306 at 256 call frames.
Permissions & host callsAll 14 standard modules route through the exact same capability-checked host bridge as the AST interpreter.

What GRAB 0.9 does not include

Native machine-code compilation (JIT), on-disk bytecode cache files across restarts, speculative type-unsafe optimizations, or GRAB 1.0 / Grex JS / CMS features remain deferred.
