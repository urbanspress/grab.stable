GRAB 0.6: Persistent Multi-Route Application Server (GRAB Server)

GRAB 0.6 transforms grab serve from a single-page localhost previewer into a persistent, high-throughput web and API server. Programs compile once on load, serve multiple route URLs with HTML templates or lossless JSON, isolate every visitor in a clean execution frame, shed overload safely instead of crashing, and run standalone or behind Nginx.

In one sentence: Your GRAB app loads once in memory and stays fast, isolated, and predictable under real website traffic—serving pages, JSON APIs, and static files safely without re-reading source files on every click.

Why GRAB 0.6 Matters (In Plain English)

How specifications/GRAB-SERVER-SPEC-006.md helps both builders and website visitors.

Builder What It Does for the Coder

  • Full multi-page sites & APIs in one readable file: Write route "GET" "/products/{id}" using req ... end alongside server.html and server.json—no sprawling framework boilerplate.
  • Load once, serve forever: GRAB lexes, parses, checks routes, and validates HTML templates once at startup into an immutable PreparedApp—zero repeated parsing overhead per request.
  • Zero-downtime safe reloads: If you reload with a typo in your code, GRAB keeps serving your last working version instead of taking the site down.
  • Ready for Nginx or standalone hosting: Works locally on 127.0.0.1:8080 out of the box, sits cleanly behind Nginx with --trusted-proxy, and exposes /_health, /_ready, and structured JSON logs.

Visitor What It Does for the Website Visitor

  • Less repeated work: Prepared routes and templates avoid reading and parsing the app again on every page click. Optional static files support ETags for conditional requests.
  • Separate visitor variables: Each request gets fresh bindings. Changing a variable in one route execution does not change the startup settings or another visitor's variables.
  • Graceful behavior during traffic spikes or glitches: If one page hits an unexpected bug or traffic surges, that request fails safely (clean 500 or 503) while the rest of the website stays online for everyone else.
  • Built-in web security: Escaped HTML templates, safe redirect checking, IP-spoofing protection (--trusted-proxy), body-size limits, and strict secret redaction in logs come enabled automatically.

Implemented Features in Action

Examples aligned directly with specifications/GRAB-SERVER-SPEC-006.md.

1. Multi-Route Web Pages & JSON APIs (route + use server)

PreparedApp · Static Conflict Checks

Shared settings run once at startup. Each route runs only when its URL and HTTP method match, with URL parameters like {id} unpacked cleanly onto req.params.

store_app.grab
use server use text use math # Runs ONCE at startup (immutable baseline) set store_name to "Northbound Goods" set tax_rate to 0.08 route "GET" "/" using req give back server.html using "home.grab.html", record {title: store_name} end route "GET" "/api/products/{id}" using req set taxed to math.round using (19.95 times (1 plus tax_rate)), 2 give back server.json using 200, record {sku: req.params.id, price: taxed} end
API Response GET /api/products/A-17 → 200 OK
Content-Type: application/json; charset=utf-8
{"sku":"A-17","price":21.55}
Preflight safety: Duplicate routes (like two GET /api/products/{id} routes) or invalid .grab.html templates are caught immediately by grab check before the server even starts.
Developer benefit: Clean URL routing, escaped HTML responses, and exact-decimal JSON APIs without external frameworks.
Visitor benefit: Fast page transitions and accurate financial figures (21.55) directly from the server.

2. Production Safeguards: Backpressure, Proxy Trust & Safe Reloads

ADR-005 · ADR-011 · ADR-015

Built-in operational limits protect memory and CPU under load, verify reverse proxies explicitly, probe health automatically, and shield secret headers from logs.

Behind Nginx Reverse Proxy
$ grab serve --addr 127.0.0.1:8765 \ --trusted-proxy 127.0.0.1,::1 \ --static public \ --max-concurrency 64 --max-queue 128 \ --request-timeout 10s --log-format json \ --diagnostics production store_app.grab grab: serving store_app.grab at http://127.0.0.1:8765/
Health, Readiness & Overload Protection
# Fast liveness & readiness probes: GET /_health → 200 OK {"status":"ok"} GET /_ready → 200 OK {"status":"ready","in_flight":4,"max_concurrency":64} # During graceful shutdown (SIGINT/SIGTERM): GET /_ready → 503 {"status":"draining"} # When queue saturates (128+ waiting): GET /api/... → 503 Service Unavailable (Retry-After: 1)
Developer benefit: Production-grade timeouts, secret-redacted JSON logs, and atomic reloads built straight into grab serve.
Visitor & operator benefit: Predictable overload handling, explicit proxy trust, and a configurable drain period for in-flight requests during shutdown.

3. Try the Working Store App

HTML · JSON · Forms · Redirects

The checked-in example has a home page, a product API, an order endpoint, a name form, and a redirect. JSON bodies use server.parse_json; URL-encoded form values are available in req.form.

From the repository folder
go run ./cmd/grab check examples/server_app.grab go run ./cmd/grab serve --reload examples/server_app.grab GET / → escaped HTML home page GET /api/products/A-17 → exact-number JSON POST /api/orders → 201 on valid order JSON POST /greet → HTML greeting from a form GET /start → 302 redirect home
Builder: Copy server_app.grab and its template; see the run guide.
Visitor: The same small app serves readable pages and data without sharing request variables.

Default limits: 64 active requests, 128 queued, 1 second queue wait, 10 seconds execution, and 1 MiB bodies. Overload returns 503, execution timeout 504, and oversized bodies 413. Use --reload on Windows or Unix; Unix also supports SIGHUP. Invalid reloads keep the last working app. Handler and route benchmarks are available; these are not a production capacity guarantee.
