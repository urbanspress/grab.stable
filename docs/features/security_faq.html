Frequently Asked Questions

Q1 Can a visitor or attacker edit our website using Chrome DevTools?

No. Nothing in Chrome DevTools touches your server or affects other visitors.

When someone opens Chrome DevTools (or presses F12) and changes colors, text, or CSS styling, they are solely editing the temporary memory of the browser running on their own local screen. It is like writing with a pencil on a printed flyer received in the mail—it has zero effect on the original document stored on the server.

Instant Reset: As soon as the user refreshes the page (F5), the server delivers a fresh copy of the site. No other user in the world ever sees their local changes.

Q2 Can an attacker inject malicious scripts or malware through user comments or forms?

No. GRAB's two-layer defense stops injection attacks automatically:

Layer 1 — Context-Aware HTML Escaping: Every dynamic value inserted into a .grab.html template is automatically sanitized. If an attacker inputs <script>steal()</script>, GRAB transforms it into harmless text: &lt;script&gt;steal()&lt;/script&gt;. The browser displays it as plain characters on the screen; it never becomes executable code.

Layer 2 — Content Security Policy (CSP): Grisp sends strict HTTP security headers commanding the visitor's browser: "Do not execute any inline scripts or external plugins." The browser outright blocks unauthorized scripts.

Q3 Can a hacker steal user data using an injected <style> tag?

No. Modern browsers cannot execute JavaScript inside CSS, and Grisp blocks external data leaks.

In theoretical legacy attacks, attackers tried using CSS background images to phone home character-by-character to a remote server. In Grisp, this attack is completely prevented:

  • GRAB auto-escaping prevents attackers from injecting active <style> tags into user content.
  • Grisp's default-src 'self' policy strictly commands the browser to reject connections to any outside domain, preventing data exfiltration.

Q4 Why did our dark-mode styling initially appear as plain text, and how was it solved?

It was Grisp's default-deny security policy actively protecting the browser.

By default, Grisp commands browsers to only load stylesheets from dedicated external files (such as /style.css) and block inline styles written directly inside the HTML page. Because our initial test template had CSS directly inside <style> tags, the browser obeyed Grisp's security rules and fell back to unstyled text.

The Fix: We updated Nginx to permit style-src 'self' 'unsafe-inline'. This allows full visual CSS styling while continuing to 100% block all JavaScript execution and external plugins.

Q5 How does GRAB protect databases from SQL Injection?

SQL injection is eliminated at the language compiler level.

In traditional PHP or Python, developers can accidentally write dynamic SQL queries using string concatenation (e.g., "SELECT * FROM users WHERE name = " + input). GRAB 0.7 does not permit dynamic raw SQL strings. All database queries must be declared as static prepared statements with typed parameters. User inputs are always treated as data values, never as executable code.

Q6 How does loopback isolation protect the Grisp server on a live VPS?

Grisp is physically unreachable from the public internet.

Grisp binds strictly to the internal loopback IP 127.0.0.1:8765. The VPS firewall drops all incoming public traffic targeting that port. Public requests only enter through Nginx on ports 80/443, which verifies TLS certificates, enforces rate limits, and proxies clean requests to Grisp.
